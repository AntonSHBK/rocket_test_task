# CheckStock

CheckStock — сервис складского учёта товаров. Он хранит физические, зарезервированные
и доступные остатки, учитывает межскладские перемещения, резервы FBS, поставки FBO
и историю складских операций.

Серверная часть реализована на FastAPI и асинхронном SQLAlchemy, данные хранятся
в PostgreSQL, миграции выполняются через Alembic. Проект запускается с помощью
Docker Compose.

## Стек

- Python 3.12
- FastAPI
- PostgreSQL 16
- SQLAlchemy и asyncpg
- Alembic
- Pydantic Settings
- pytest
- Docker Compose

## Сборка и запуск

Соберите образы и запустите сервисы в фоновом режиме:

```powershell
docker compose -f docker/docker-compose.yml up --build -d
```
При первом запуске PostgreSQL автоматически создаст пользователя и базу данных
из `docker/.env`. После перехода PostgreSQL в состояние `healthy` backend выполнит проверку миграций
`alembic upgrade head` и запустит сервер Uvicorn.

После запуска доступны:

- Основная страница: [http://127.0.0.1:8000/](http://127.0.0.1:8000/)
- API: [http://127.0.0.1:8000/api](http://127.0.0.1:8000/api)
- Swagger UI: [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs)
- OpenAPI: [http://127.0.0.1:8000/openapi.json](http://127.0.0.1:8000/openapi.json)

## Добавление тестовых данных

Загрузите подготовленные товары, склады и начальные остатки:

```powershell
docker compose -f docker/docker-compose.yml exec backend python -m app.migrations.seed
```

или выполните в контейнере:

```sh
python -m app.migrations.seed
```

## Ключевые решения

### Архитектура

Проект реализован как монолитное FastAPI-приложение:

- `routers` принимают HTTP-запросы и формируют ответы;
- `schemas` валидируют входные и выходные данные через Pydantic;
- `service` содержит складскую бизнес-логику и управляет транзакциями;
- `models` описывают ORM-модели SQLAlchemy;
- `template` и `static` содержат Jinja2-шаблоны, CSS и JavaScript;
- `migrations` хранит миграции Alembic и загрузчик тестовых данных.

Подключение к PostgreSQL полностью асинхронное.

### Учёт остатков

Остаток хранится отдельно для каждой пары «товар — склад»:

- физический остаток — товар, фактически находящийся на складе;
- зарезервированный остаток — товар, закреплённый за активными резервами FBS;
- доступный остаток рассчитывается как `физический − зарезервированный`.

Складские операции разрешены только в пределах доступного остатка. Товары,
которые уже отправлены между складами, на маркетплейс или клиенту, учитываются
отдельно как товары в пути и не входят в физический остаток склада.

На уровне PostgreSQL добавлены ограничения положительного количества,
неотрицательных физических и зарезервированных остатков, а также запрет ситуации,
когда резерв превышает физический остаток.

### Складские операции

Реализованы следующие сценарии:

- приход товара увеличивает физический остаток выбранного склада;
- списание уменьшает только доступное количество и сохраняет причину;
- межскладское перемещение проходит состояния «Создано», «В пути» и «Принято»;
- FBS поддерживает создание резерва, отмену, отправку и подтверждение доставки
  заказа клиенту;
- FBO поддерживает создание поставки, отправку и подтверждение приёмки
  маркетплейсом;
- нехватка товара на выбранном складе возвращается как ошибка `409 Conflict`
  с доступным количеством и остатками на других активных складах.

Удаление склада реализовано как архивация. Запись склада, его остатки и история
сохраняются, но новые операции с архивным складом запрещены. Склад можно снова
разархивировать.

### Целостность данных

Изменение остатков, статуса операции и запись в историю выполняются в одной
транзакции PostgreSQL. Для операций списания и смены состояния используется
`SELECT FOR UPDATE`, поэтому конкурентные запросы не могут одновременно списать
один и тот же доступный остаток.

Создание прихода, списания, перемещения, резерва FBS и поставки FBO защищено
ключом идемпотентности. Повторный запрос с тем же ключом и теми же параметрами
возвращает ранее созданный результат без повторного изменения остатков. Попытка
повторить тот же ключ с другими параметрами возвращает конфликт.

Каждая завершённая складская операция регистрируется в истории с типом события,
артикулом, количеством, отправителем, получателем и временем выполнения.

### REST API и веб-интерфейс

FastAPI автоматически формирует OpenAPI-схему и Swagger UI. Запросы и ответы
валидируются Pydantic-схемами, а прикладные исключения возвращаются в едином
JSON-формате.

Веб-интерфейс построен на Jinja2, HTML, CSS и JavaScript без отдельного
frontend-фреймворка. Реализованы три страницы:

- `/` — остатки, товары в пути, приход и списание;
- `/warehouses` — склады, архив и межскладские перемещения;
- `/operations` — операции FBS/FBO и история складских событий.

Общий JavaScript-клиент обращается к REST API, блокирует кнопки на время запроса,
показывает ошибки и обновляет связанные таблицы без перезагрузки страницы.

### Логирование

Приложение использует единый логер `api`. Сообщения выводятся в stdout контейнера
и записываются в файлы с ротацией:

- `logs/api.log` — сообщения уровня `INFO` и выше;
- `logs/api.warning.log` — предупреждения и ошибки.

Успешные бизнес-операции логируются после завершения транзакции. Нехватка товара
и запрещённые переходы состояний записываются с уровнем `WARNING`. Пароли и тела
HTTP-запросов в бизнес-логи не попадают.

### Тестирование

Тесты покрывают модели, расчёт остатков, приходы и списания, управление складами,
перемещения, FBS/FBO, историю, идемпотентность, обработку нехватки и HTML-страницы.

Запуск полного набора тестов в контейнере:

```powershell
docker compose -f docker/docker-compose.yml exec backend pytest -q
```
