Система предназначена для менеджера интернет-магазина, который работает с несколькими складами и маркетплейсами.

Например, магазин продаёт органайзеры, контейнеры и корзины. Товары могут одновременно находиться:
- На складе «Север».
- На складе «Юг».
- В резерве под заказ покупателя.
- В процессе перемещения между складами.
- В пути на склад маркетплейса.
- В пути к конечному покупателю.
Цель: предоставить менеджеру единый интерфейс, в котором он сможет увидеть местонахождение каждой единицы товара и выполнить основные складские операции.

В задании предусмотрены три функциональных блока: экран остатков, управление складами и перемещениями, обработка отправок FBS/FBO. Дополнительно обязательны история операций и корректный учёт при повторном подтверждении.

2. Расшифровка терминологии
Прежде чем переходить к реализации, необходимо разобраться с используемыми сокращениями.
Термин	Расшифровка и значение
CheckStock	Название приложения. Условно — «Проверка остатков».
SKU	Stock Keeping Unit — единица складского учёта. Уникальный артикул товара, например SKU-101.
ФФ	Фулфилмент — склад или логистический оператор, выполняющий хранение и обработку товаров.
FBS	Fulfillment by Seller — выполнение заказа продавцом. Товар хранится у продавца или его оператора, после заказа отправляется покупателю через логистическую схему маркетплейса.
FBO	Fulfillment by Operator — выполнение заказа оператором маркетплейса. Продавец заранее поставляет товар на склад маркетплейса, где он хранится до продажи.
API	Application Programming Interface — программный интерфейс для взаимодействия фронтенда и сервера.
REST API	Representational State Transfer — архитектурный стиль построения HTTP API, где ресурсы доступны через URL и стандартные методы HTTP.
FastAPI	Python-фреймворк для разработки серверных API.
PostgreSQL	Реляционная система управления базами данных.
README	Файл с описанием проекта, инструкцией запуска, архитектурой и проверками.
UI	User Interface — пользовательский интерфейс.
Транзакция	Группа операций с базой данных, которая выполняется целиком либо полностью отменяется.
Идемпотентность	Свойство операции, при котором её повторное выполнение не приводит к повторному изменению результата.

Разница между FBS и FBO
Упрощённая схема двух способов выполнения заказов. В реальной FBS-логистике между продавцом и покупателем могут участвовать сортировочные центры маркетплейса.
В контексте тестового задания:

FBS: товар сначала резервируется на конкретном складе. При отправке физический остаток этого склада уменьшается, а товар переходит в состояние «В пути к клиенту».

FBO: товар отправляется со склада фулфилмента на склад маркетплейса. После отправки он больше не числится на исходном складе, но продолжает учитываться как товар в пути до подтверждения приёмки.

3. Что именно требуется разработать
3.1. Экран остатков товаров
Это основная страница приложения.

Менеджер должен видеть список всех товаров, их артикулы и распределение по складам.

В задании предусмотрены следующие тестовые данные:
Артикул	Наименование	Север	Юг	Всего
SKU-101	Органайзер	10	6	16
SKU-102	Контейнер	5	0	5
SKU-103	Корзина	0	4	4
Итого		15	10	25

Эти количества необходимо использовать для начального прихода товаров. 
CheckStock.pdf

Для каждого артикула и склада необходимо отображать три основных показателя.

Физический остаток (Physical Stock) — количество товара, которое фактически находится на складе.

Резерв (Reserved Stock) — количество товара, уже закреплённое за заказами FBS, но ещё не отправленное.

Доступный остаток (Available Stock) — количество товара, которое можно использовать для новых операций.

Формула:
\[
Q_{\text{available}}=Q_{\text{physical}}-Q_{\text{reserved}}
\]

Например, на складе «Север» физически находится 10 органайзеров. Менеджер зарезервировал 3 штуки под заказ FBS.

При этом отдельно необходимо отображать товар, находящийся:
- В пути между двумя складами ФФ.
- В пути на склад маркетплейса по FBO.
- В пути к клиенту по FBS.
Важно: эти количества нельзя включать в физические остатки складов, поскольку товар уже покинул склад отправления.
Что нужно реализовать
На фронтенде — таблицу остатков с группировкой по артикулам и складам, а также отдельный блок товаров в пути.

На бэкенде — API, которое рассчитывает или возвращает все перечисленные показатели.

В базе данных — хранение информации о товарах, складах, остатках, резервах и отправках.
3.2. Управление складами фулфилмента
Следующая функциональность — создание, переименование и удаление складов.

Пример интерфейса:
ID	Название	Количество товаров	Действия
1	Север	15	Переименовать / Удалить
2	Юг	10	Переименовать / Удалить

Пользователь должен иметь возможность создавать новый склад, например «Центр», переименовывать существующие склады и удалять их.

Однако здесь есть важный нюанс задания:

При удалении склада необходимо сохранить остатки и историю операций.

Это означает, что нельзя просто выполнить SQL-запрос DELETE FROM warehouses WHERE id = 1, если на складе есть товары.

Иначе можно потерять связь между историческими операциями и складом.
Рекомендуемая реализация
Использовать механизм Soft Delete — логического удаления.

В таблице складов предусмотреть поле:
is_active: bool = True



При удалении склада устанавливать is_active = False, сохраняя саму запись.

Если на складе остались товары, можно выбрать следующую политику:
1. Склад становится архивным.
2. Его остатки продолжают отображаться в специальном разделе.
3. Новые операции с архивным складом запрещаются.
4. Исторические операции остаются доступными.
Это один из возможных вариантов реализации. В исходном задании конкретная политика удаления не определена. Альтернативный вариант — запрещать удаление до перемещения всех товаров, но требование «при удалении сохраните остатки и историю» лучше демонстрируется именно архивированием.
3.3. Приход товара на склад
Приход — операция увеличения физического остатка товара на определённом складе.

Например, менеджер оформляет поступление:
- Товар: SKU-101.
- Склад: «Север».
- Количество: 5.
До операции на складе находилось 10 единиц.

После операции:
\[
Q_{\text{physical}}=10+5=15
\]

Необходимо:
1. Проверить существование артикула и склада.
2. Проверить, что количество положительное.
3. Увеличить физический остаток.
4. Сохранить операцию в истории.
5. Вернуть обновлённые остатки.
Для реализации можно предусмотреть API:
POST /api/receipts


Пример запроса:
{
  "sku": "SKU-101",
  "warehouse_id": 1,
  "quantity": 5
}


Приход должен выполняться в транзакции базы данных, чтобы изменение остатка и запись истории не могли разойтись.
3.4. Перемещение товаров между складами
Это более сложная операция.

Предположим, менеджер хочет переместить 4 органайзера со склада «Север» на склад «Юг».

Исходное состояние:
Показатель	Север	Юг	В пути
SKU-101	10	6	0

После оформления отправки:
Показатель	Север	Юг	В пути
SKU-101	6	6	4

После подтверждения приёмки:
Показатель	Север	Юг	В пути
SKU-101	6	10	0

Обратите внимание: нельзя сразу прибавлять товар к остатку склада назначения. Между отправкой и приёмкой он находится в пути.

Для перемещения можно использовать три состояния:
Создано
CREATED
В пути
IN_TRANSIT
Принято
RECEIVED

Предлагаемая модель жизненного цикла межскладского перемещения.
Рекомендуемые API:
POST /api/transfers
POST /api/transfers/{id}/ship
POST /api/transfers/{id}/receive


Первый запрос создаёт перемещение, второй списывает товар со склада отправления и переводит его в путь, третий подтверждает приёмку.

Чтобы не усложнять тестовое задание, можно объединить создание и отправку в одну операцию. Тогда останутся два основных действия: «Отправить» и «Принять».

4. Реализация FBS — резервирование и отправка покупателю
FBS — один из ключевых бизнес-процессов задания.

Менеджер получает заказ покупателя и должен зарезервировать товар на конкретном складе.

Рассмотрим пример.

На складе «Север» находится 10 органайзеров. Покупатель оформляет заказ на 3 единицы.
Этап 1. Создание резерва
Система проверяет доступное количество товара.

Если товара достаточно, создаётся резерв.
Показатель	До	После
Физический остаток	10	10
Резерв	0	3
Доступно	10	7
В пути к клиенту	0	0

Физический остаток не уменьшается, поскольку товар ещё находится на складе.
Этап 2. Отправка заказа
После фактической отправки товара покупателю:
Показатель	До	После
Физический остаток	10	7
Резерв	3	0
Доступно	7	7
В пути к клиенту	0	3

Здесь происходит два изменения: уменьшается физический остаток и снимается резерв. Товар переводится в категорию «В пути к клиенту».
Этап 3. Отмена резерва
Если покупатель отменяет заказ до отправки, необходимо освободить зарезервированное количество.

При этом физический остаток не меняется.

Рекомендуемые API:
POST /api/fbs/reservations
POST /api/fbs/reservations/{id}/cancel
POST /api/fbs/reservations/{id}/ship


Важный нюанс: в задании не требуется моделировать возвраты товаров или полную доставку FBS. Поэтому для минимальной версии достаточно реализовать резервирование, отмену и отправку. Дополнительные статусы доставки необязательны.

5. Реализация FBO — отправка на склад маркетплейса
В отличие от FBS, здесь товар не резервируется под конкретного покупателя.

Менеджер формирует поставку, которая отправляется на склад маркетплейса.

Предположим, на складе «Север» находится 10 органайзеров. Необходимо отправить 6 единиц на склад маркетплейса.

После отправки:
Показатель	До	После
Физический остаток ФФ	10	4
В пути FBO	0	6
Принято маркетплейсом	0	0

После приёмки маркетплейсом:
Показатель	До	После
Физический остаток ФФ	4	4
В пути FBO	6	0
Принято маркетплейсом	0	6

Последний показатель я рекомендую добавить, чтобы принятый маркетплейсом товар не исчезал из учёта.

В исходном задании требуется учитывать товар в пути до приёмки, но не уточняется, нужно ли вести дальнейший учёт остатков непосредственно на маркетплейсе. Для тестового прототипа достаточно накопительного показателя «Принято маркетплейсом» без полноценной модели склада маркетплейса.

Рекомендуемые API:
POST /api/fbo/shipments
POST /api/fbo/shipments/{id}/receive



6. Обработка нехватки товара
Это отдельное обязательное требование.

В задании специально указано, что необходимо обработать ситуацию, когда на выбранном складе товара недостаточно, но суммарно на всех складах товара хватает.

Рассмотрим пример.
Склад	Доступно SKU-101
Север	2
Юг	8
Всего	10

Менеджер пытается зарезервировать 5 органайзеров со склада «Север».

Несмотря на то что общий остаток равен 10, операцию выполнять нельзя, поскольку на выбранном складе доступно только 2 единицы.

Система должна:
1. Определить недостаток на выбранном складе.
2. Отклонить резервирование или отправку.
3. Не изменять остатки.
4. Вернуть понятную ошибку.
5. Желательно показать наличие товара на других складах.
Пример ответа API:
{
  "error": "INSUFFICIENT_STOCK",
  "message": "Недостаточно товара на складе Север",
  "requested": 5,
  "available": 2,
  "other_warehouses": [
    {
      "warehouse_id": 2,
      "name": "Юг",
      "available": 8
    }
  ]
}


Для такого случая логично использовать HTTP-статус 409 Conflict — конфликт операции с текущим состоянием ресурсов.

Автоматически переносить товар с другого склада не требуется. Достаточно корректно обработать ошибку и предложить менеджеру выполнить перемещение.

7. История операций и защита от повторного списания
Этот пункт существенно влияет на оценку.

В задании указано, что должна существовать история операций, в которой видно, какой товар, в каком количестве, откуда и куда переместился.

Также повторное подтверждение операции не должно приводить к двойному списанию.
7.1. История операций
Предлагаю предусмотреть журнал, который фиксирует каждое значимое складское событие.

Например:
Дата	Операция	Артикул	Кол-во	Откуда	Куда
12.11	Приход	SKU-101	10	Поставка	Север
12.11	Резерв FBS	SKU-101	3	Север	Резерв
12.11	Отправка FBS	SKU-101	3	Север	Клиент
12.11	Перемещение	SKU-102	2	Север	В пути к Югу
12.11	Приёмка	SKU-102	2	В пути	Юг

Это пример интерфейса, а не готовые данные из задания.

Для каждой записи полезно сохранять идентификатор операции, тип события, артикул, количество, исходный и целевой объекты, время выполнения и идентификатор связанного заказа или перемещения.
7.2. Идемпотентность операций
Рассмотрим ситуацию: менеджер нажимает «Принять перемещение», но браузер не получает ответ от сервера из-за сетевого сбоя.

Менеджер нажимает кнопку повторно.

Если система каждый раз выполняет прибавление количества, остаток станет неправильным.

Например:
- На склад «Юг» должно поступить 4 единицы.
- Первый запрос добавил 4 единицы.
- Второй запрос повторно добавил ещё 4.
- В результате склад получил 8 вместо 4.
Чтобы исключить такую ситуацию, необходимо проверять состояние операции.

Пример:
if transfer.status == "RECEIVED":    return transfer



Но одной проверки в Python недостаточно при конкурентных запросах. Два запроса могут одновременно прочитать старый статус.

Поэтому правильнее использовать транзакции PostgreSQL и блокировку строки (SELECT ... FOR UPDATE) либо атомарное условное обновление.

Общая последовательность:
1. Начать транзакцию.
2. Заблокировать запись перемещения.
3. Проверить статус.
4. Если операция уже выполнена — вернуть существующий результат.
5. Иначе изменить остатки и статус.
6. Добавить запись в журнал.
7. Зафиксировать транзакцию.
Это обеспечит защиту от повторной приёмки даже при одновременных запросах.

Для операций создания также полезен idempotency_key — уникальный ключ запроса, позволяющий отличать повторную отправку того же действия от нового действия.
